# Plan: BL-78 — Configurable counting classes at deployment (multi-species, model-driven)

## Summary

Make the counted class(es) configurable at deployment instead of hardcoded `== 1`. The model build captures class metadata (`nc`, `names`, `default_counting_class`, dataset version) into `app/model/classes.yaml` (source of truth). At runtime the app loads it, publishes a read-only `/conf/model-classes.json` mirror (IPC file #5, app→companion), and resolves the effective `counting_class_ids` set via 3 levels (model default → companion override in `runtime-settings.json` → validated against `model-classes.json`). A single OC-SORT runs on the counting set; per-species sub-counters exist alongside the global counter (global = sum of sub-counters, retro-compatible). The companion (BL-80, sister repo) is out of scope — BL-78 only *writes* `model-classes.json` + *reads* `counting_class_ids` from `runtime-settings.json`.

GitHub issue: https://github.com/wloonis/animal-counter/issues/98

## Architecture Decisions

- **Single OC-SORT tracker on the `counting_class_ids` set** (class id preserved per track); no per-species trackers. Guards (mirror, resurrection, reid) operate on the unified set. Rationale: multi-tracker would fragment track state and break the cross-class re-ID/re-ID guards that rely on a single ID space.
- **`inference.py` keeps ONLY the `counting_class_ids` set before OC-SORT** (drop non-counted classes like human), consistent with today dropping class 0. OC-SORT sees exactly the counted species. Rationale: matches existing behavior; non-counted detections never enter the tracker, avoiding spurious tracklets.
- **Global counter = sum of sub-counters, stays always** (retro-compatible). `counter_to_right` remains the single visible global; per-species sub-counters are additive above it. The global is the invariant the validation videos check (12/30/42/35).
- **`default_counting_class` = model property**, captured at build from `TRAINING_DEFAULT_COUNTING_CLASS` (default 1 today, convention future 0 = target species). Fail-fast validation that the ID exists in `data.yaml` + log resolved name. Rationale: the model defines its own target class; deployment only narrows/adds to the set.
- **`counting.py` `counting_class` single-int param → `counting_class_ids` set**; `== counting_class` → `in counting_class_ids` at all guard/crossing sites. Rationale: minimal, surgical change preserving every guard invariant; the set membership test is a strict generalization of the int equality.
- **`runtime-settings.json` `counting_class_ids` validated against `model-classes.json`**; invalid IDs logged + dropped; fallback `[default_counting_class]` when absent/invalid. Rationale: the companion (BL-80) may only propose classes the model knows; the app is the authority on what the model can count.
- **Per-recording resolution** (like `offset_counting_line`): `counting_class_ids` is resolved in `main.py::start()` hot-reload block and stored in `shared_state` for the lifetime of that recording. Mid-recording hot-reload of the *counted set* is NOT supported (a tracker-state change mid-recording is undesirable); a change takes effect on the next recording. Rationale: consistent with `offset_counting_line` semantics already documented in IPC_CONTRACT.md.
- **Backward compatibility when `classes.yaml` is absent** (legacy deployed model without it): fall back to `CLASS_NAMES = ['human', 'pig']`, `default_counting_class = 1`, `counting_class_ids = [1]` — i.e. the exact pre-BL-78 behavior. Rationale: existing models in the field have no `classes.yaml`; the app must boot and count identically until a rebuild produces one.
- **Keep OC-SORT, FPS_OUTPUT=30, H=0, COUNTING_LOST_BUFFER_FRAMES=60 vs COUNTING_GUARD_MAX_AGE=15 decoupled** (AGENTS.md constraints). None of these are touched.
- **`jetson-validate` uses `--full` per-run override** (not `config.json` commit, not workflow YAML auto-detect). The launch message / relay instructs the node to pass `--full`.

## Risks

- **Legacy model without `classes.yaml`** — existing deployed models have no `classes.yaml`. Mitigation: `load_classes_yaml()` fail-opens to `None`; `shared_state` `__init__` defaults (`['human','pig']`, `1`, `[1]`) reproduce pre-BL-78 behavior exactly. A rebuild (Task 2) is required to produce `classes.yaml`; until then the app is byte-for-byte equivalent in counting.
- **Sub-counter drift from global** — if a sub-counter +1/-1 path is missed, the global (sum) and sub-counters diverge, breaking the invariant. Mitigation: every `counter_to_right += 1`/`-= 1` site in `counting.py` gets a matching `sub_counts[class_id] += 1`/`-= 1` in the same branch; the validation `--full` run checks the global against 12/30/42/35 (the global is the sum, so a divergence surfaces as a count mismatch).
- **`counting_class_ids` change mid-recording** — a companion writing `counting_class_ids` during an active recording would not take effect until the next recording (per-recording resolution). Mitigation: documented in IPC_CONTRACT.md (same semantics as `offset_counting_line`); the `main.py` hot-reload block runs at `start()`, not mid-frame.
- **Invalid `counting_class_ids` from companion** — a malformed/unknown ID could silently zero the count. Mitigation: `resolve_counting_class_ids()` validates each ID against `model-classes.json` names, drops invalid ones with a WARNING log, and falls back to `[default_counting_class]` only when the entire set is absent/all-invalid (never an empty set).
- **`data.yaml` parse at build** — Roboflow `data.yaml` is YAML; parsing in Ansible needs `from_yaml` or a `python3 -c` shim. Mitigation: use Ansible's `slurp` + `from_yaml` filter (stdlib in Ansible core); fail-fast on parse error with a clear message.
- **`model-classes.json` write on read-only `/conf`** — `/conf` is RW (BL-79 mounted it RW for `runtime-settings.json`), so the app can write `model-classes.json` there. Mitigation: best-effort write with WARNING log on failure; the app continues counting even if the mirror can't be published (the companion just won't see the class catalog until the next successful write).
